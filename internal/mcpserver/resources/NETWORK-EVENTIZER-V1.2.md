# xqnet Network Eventizer Algorithm v1.2

Status: implementation contract for `xqnet` `network-reference-v1.2`.

This document defines deterministic processing choices that are intentionally not normative in Crosscue Event Model Network Profile 0.1.

## 1. Purpose

Network Profile 0.1 defines semantic compositions and constraints. `network-reference-v1.2` defines how this reference implementation maps supported Zeek and Suricata evidence into those semantics and into analytical projections.

## 2. Semantic boundary

`xqnet` does not replace source-native network evidence.

```text
PCAP / live traffic
      ↓
Zeek / Suricata
      ↓
structured source evidence
      ↓
xqnet network-reference-v1.2
      ↓
Core Events + projections
```

PCAP parsing, stream reassembly and application protocol decoding are upstream-engine responsibilities.

## 3. Reference adapters

### zeek-reference-v1

Supported logs:

- `arp.log` generated by the bundled ARP script in PCAP mode;
- `conn.log`;
- `dns.log`;
- `dhcp.log`;
- `ssl.log`;
- `known_services.log`;
- `software.log`.

PCAP mode also loads Zeek Community ID logging with seed `0`.

### suricata-reference-v1

Supported EVE types include:

- `flow`;
- `dns`;
- `tls`;
- `arp`;
- `dhcp`;
- application evidence such as HTTP/HTTP2/SSH/SMTP/IMAP/FTP/PostgreSQL/SMB/QUIC.

Suricata alerts are not promoted to compromise assessments by this reference algorithm.

## 4. Entity ladder

The reference implementation keeps these concepts distinct:

```text
interface → address → endpoint → service
```

A MAC is interface-scoped by default. IP/MAC evidence does not itself justify a device entity. An address/port/protocol tuple is an endpoint; application evidence is required before a service entity is materialized.

## 5. ARP

ARP supplies evidence that an interface asserted an address at the observation point.

Repeated source ARP records for the same interface/address pair are coalesced to one semantic:

```text
xq.net:address_binding / xq.net:first_observed
```

Core class is `derived`. The `bindings` projection retains first/last observation and the complete source-evidence count.

Ambiguous bindings are retained; an IP observed with two MAC interfaces is not collapsed to one identity.

## 6. Connections and sessions

A connection observation targets an endpoint, never a service.

Zeek uses its originator/responder semantics directly. Its `conn.log` timestamp
is the first-packet time, while the record includes whole-connection counters,
state and application evidence. The connection Core Event is therefore anchored
at the reported interval end (`ts + duration`), with `source_interval_start` and
`source_interval_end` retained in context. Session projections retain the original
start and end. Connection-derived entity, service, presence and relationship
evidence uses the corrected event time; the first relationship parent is the
earliest qualifying completed connection, not necessarily the earliest start.

Duration must be supplied, finite, non-negative and representable as a Go
`time.Duration` (less than approximately 292 years). Missing, null, malformed,
negative, non-finite or out-of-range duration rejects processing with a source
line error. Explicit zero is supported; missing duration is never guessed as
zero. This deliberately rejects native Zeek records that lack enough timing
evidence to place their summary.

Suricata whole-flow summaries remain timestamped at `flow.end`; the source flow
interval remains context. When protocol evidence supports client/server role,
the Suricata adapter orients the semantic subject/object accordingly. Otherwise
source/destination orientation is retained and explicitly marked as weaker
evidence rather than guessed from port numbers.

A session is an analytical projection. Different upstream engines may sessionize the same transport tuple differently.

## 7. Communication relationships

A communication relationship is derived from qualifying connection evidence and is emitted as:

```text
xq.net:communication_relationship / xq.net:first_observed
```

`first_observed` is not `established`.

TCP attempts lacking adequate responder evidence do not automatically become relationships. One-way UDP/multicast may form an `unidirectional_observed` relationship because one-way traffic can itself be meaningful.

The first-observed Core Event contains only facts available from the first qualifying parent connection. Whole-window counts, bytes, last-observed time, aggregate directionality and later application evidence stay in `relationships.parquet`.

## 8. Community ID

Community ID seed `0` is used for Zeek PCAP mode and recommended for Suricata.

Community ID correlates a transport tuple; it does not define a session. One relationship may aggregate many Community IDs and one Community ID may correspond to different session counts in different engines.

## 9. DNS

Query and response knowledge remain temporally separate.

- a query event contains query-side facts only;
- answer-derived resolution/alias events occur at response evidence time;
- a response-only source record does not manufacture a missing query observation;
- DNS `A`/`AAAA` owner→address and CNAME owner→alias relationships are distinct;
- Suricata detailed answers are preferred over grouped answers when both exist, because detailed records retain RR owners.

## 10. TLS and application services

TLS session events always target the transport endpoint. SNI is represented separately as a server-name binding. Application protocol evidence can materialize endpoint→service observations.

Application stacks are canonicalized deterministically (for example `xmpp,tls`).

## 11. Presence

Network presence is observer/scope dependent. It is emitted only when the operator supplies an explicit `network-id` and corresponding CIDRs. Merely observing a public resolver or remote server in a capture does not make it "present" on the monitored network.

A first-observed presence fact is not an ENTER transition, and last observation does not manufacture LEAVE.

## 12. Temporal purity

A Core Event at time T must not contain facts only supportable after T.

Whole-window summaries are projections. This rule applies to relationships, DNS transactions and source-native whole-flow summaries.

## 13. Determinism and ordering

Events are sorted by parsed event time, not timestamp-string lexical order. Parent events precede derived children at the same instant. IDs are SHA-256-derived opaque identifiers from normalized semantic/source keys.

Identical source artifacts, source identifier and eventizer configuration produce stable event/projection ordering. Source line identity remains part of source-record provenance, so materially reordered source logs are considered different evidence artifacts.

## 14. Deterministic collision-safe event IDs

`network-reference-v1.2` retains the collision-safe allocation rules introduced
in v1.1. For an unchanged semantic/source seed, the first occurrence retains its
original SHA-256 event ID. If the same seed is emitted again within the same
deterministic run, the later event receives an occurrence-qualified seed
(`|occurrence:N`) before hashing. The occurrence ordinal is also recorded as
`provenance.parameters.event_id_occurrence`.

This prevents legitimate repeated evidence within one source record (for example repeated identical DNS answers) from causing duplicate Core event IDs while preserving existing first-occurrence IDs. Allocation order follows the deterministic adapter processing order; materially reordered source artifacts remain different evidence artifacts as documented above.

## 15. Versioning

Compared with v1.1, corrected Zeek connection times change connection IDs and
dependent parent references/derived IDs, event ordering and observation times.
Suricata eventization is unchanged apart from release/eventizer provenance.
This eventizer was introduced alongside `xqnet-analysis-v0.1` and
`xqnet-mcp-v0.1`. The independently versioned analytical contract advances to
v0.2 in xqnet 0.1.3-rc3 for nanosecond storage; this does not change eventizer
semantics. Historical v1/v1.1 contract documents remain available.

Any change that can alter eventization decisions or projection semantics changes `network-reference-v1.2` to a new reference-algorithm identifier/version. Adapter-only mapping changes may additionally version the relevant `zeek-reference-v1` or `suricata-reference-v1` mapping.
